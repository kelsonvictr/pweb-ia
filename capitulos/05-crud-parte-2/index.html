O id vira endereço: /produtos/3/editar
O número da ficha entra na URL — e o Flask entrega pra função
"Conserta a ficha 3, por favor" 🗂️

No fichário de aço, você não fala "conserta a ficha do fone" — fichas têm número. Na web é igual: a URL carrega o número. /produtos/3/editar = "abre a tela de edição da ficha 3". Cada produto ganha a própria URL de edição.

A novidade no Flask é um pedaço variável na rota — e repara que ele chega como parâmetro da função:

    ...
💡 <int:id> — a lacuna da URL

O <int:id> é uma lacuna na rota (lembra das lacunas do Jinja? mesma ideia, no endereço): casa com qualquer número naquela posição e entrega o valor pra função, já convertido pra int. O int: é o segurança da porta: /produtos/abc/editar nem chega na função — 404 direto.

🧠
De onde vem esse id? Da tabela! O AUTOINCREMENT do Dia 3 carimbou um número único em cada linha — e você exibiu ele na coluna ID do estoque no Dia 4. Era preparação pra hoje. 😏

def buscar_produto(id):
    conexao = sqlite3.connect("loja.db")
    cursor = conexao.cursor()
    cursor.execute("SELECT * FROM produtos WHERE id = ?", (id,))
    produto = cursor.fetchone()   # ← UMA ficha (ou None)
    conexao.close()
    return produto


def atualizar_produto(id, nome, preco, qtd):
    conexao = sqlite3.connect("loja.db")
    cursor = conexao.cursor()
    cursor.execute(
        "UPDATE produtos SET nome = ?, preco = ?, quantidade = ? WHERE id = ?",
        (nome, preco, qtd, id)
    )
    conexao.commit()
    conexao.close()
💡 fetchone vs fetchall

fetchall = todas as fichas (uma lista de tuplas). fetchone = a primeira ficha que casou (uma tupla só) — ou None, se nenhuma casou. Como buscamos por id (que é único), é a ferramenta perfeita. E o None é o nosso jeito de descobrir a ficha 99. 👻

🧐
Detalhe fino: (id,) com vírgula. Os placeholders pedem uma TUPLA, e tupla de um elemento só em Python é (id,) — sem a vírgula seria só um parêntese. Erro clássico de digitação, guarda esse.

Excluir com respeito
Por que apagar NUNCA pode ser um simples link
A história de terror obrigatória 📖

Um sistema antigo tinha links /excluir/1, /excluir/2… Um robô de busca visitou o site e fez o que robôs fazem: clicou em todos os links. Apagou o banco inteiro, educadamente, um GET de cada vez. 💀 Moral: link (GET) é pra LER. Quem MUDA o banco é POST — robô nenhum submete formulário.

E tem o dedo humano também: apagar sem perguntar é crueldade. O padrão simples e sem JavaScript: uma página de confirmação — GET mostra o "tem certeza?", o botão (POST) executa.

def excluir_produto(id):
    conexao = sqlite3.connect("loja.db")
    cursor = conexao.cursor()
    cursor.execute("DELETE FROM produtos WHERE id = ?", (id,))
    conexao.commit()
    conexao.close()

# app.py
@app.route("/produtos/<int:id>/excluir", methods=["GET", "POST"])
def excluir_produto(id):
    produto = banco.buscar_produto(id)
    if produto is None:
        return "Produto não encontrado!", 404

    if request.method == "POST":
        banco.excluir_produto(id)
        return redirect("/produtos")

    return render_template("excluir.html", p=produto)

Duas tabelas conversando
A venda ganha tabela própria — apontando pra ficha do produto

Uma venda é um FATO: "vendi 2 fones por R$ 299,80". Fato se registra — tabela nova no criar_banco.py:

loja/criar_banco.py (adicione e rode ▶ de novo) SQL 
cursor.execute("""
    CREATE TABLE IF NOT EXISTS vendas (
        id INTEGER PRIMARY KEY AUTOINCREMENT,
        produto_id INTEGER,
        qtd INTEGER,
        total REAL
    )
""")
O post-it que aponta pra outra ficha 🗂️➡️🗂️

Repara no produto_id: a ficha de venda não copia o nome do produto — ela anota "foi o produto da ficha 1". Duas tabelas se conversando pelo número. É por isso que o banco se chama RELACIONAL — e é a primeira vez que você vê a mágica acontecer.

🤔
"Por que não gravar o nome direto?" Se o produto for renomeado amanhã, as vendas antigas continuariam com o nome velho — dados divergindo. Guardando o id, a venda sempre aponta pra verdade atual. (E economiza espaço de brinde.)

💡 Duas escritas, um destino

Toda venda = INSERT na vendas + UPDATE na produtos. E se o sistema caísse entre uma e outra? Venda registrada sem baixar estoque — dado mentiroso. Por isso as duas vão no MESMO commit: o rascunho e carimbo do Dia 3 garantindo o "tudo junto, ou nada". Você já sabia o porquê antes de precisar. 🎯

def registrar_venda(produto_id, qtd, total):
    conexao = sqlite3.connect("loja.db")
    cursor = conexao.cursor()

    cursor.execute(
        "INSERT INTO vendas (produto_id, qtd, total) VALUES (?, ?, ?)",
        (produto_id, qtd, total)
    )
    cursor.execute(
        "UPDATE produtos SET quantidade = quantidade - ? WHERE id = ?",
        (qtd, produto_id)
    )

    conexao.commit()   # ← UM carimbo pras DUAS escritas: tudo junto, ou nada
    conexao.close()

@app.route("/vender", methods=["GET", "POST"])
def vender():
    produtos = banco.listar_produtos()

    if request.method == "POST":
        produto_id = int(request.form["produto_id"])
        qtd        = int(request.form["qtd"])
        produto    = banco.buscar_produto(produto_id)

        if qtd > produto[3]:   # quantidade em estoque
            return render_template("vender.html", produtos=produtos,
                                   erro="Estoque insuficiente!")

        total = qtd * produto[2]   # qtd × preço
        banco.registrar_venda(produto_id, qtd, total)
        flash("Venda registrada! 🎉")
        return redirect("/vendas")

    return render_template("vender.html", produtos=produtos)
💡 Quem calcula o total é o SERVIDOR

O preço vem do banco (produto[2]), nunca da tela. Se o total viesse do formulário, qualquer espertinho compraria fone por R$ 0,01 editando o form. Regra de sistema: o cliente escolhe; o servidor calcula e confere.

def listar_vendas():
    conexao = sqlite3.connect("loja.db")
    cursor = conexao.cursor()
    cursor.execute("""
        SELECT vendas.id, produtos.nome, vendas.qtd, vendas.total
        FROM vendas
        JOIN produtos ON produtos.id = vendas.produto_id
    """)
    vendas = cursor.fetchall()
    conexao.close()
    return vendas


def faturamento():
    conexao = sqlite3.connect("loja.db")
    cursor = conexao.cursor()
    cursor.execute("SELECT SUM(total) FROM vendas")
    soma = cursor.fetchone()[0]   # uma linha, uma coluna
    conexao.close()
    return soma or 0   # sem vendas, SUM devolve None → vira 0
💡 JOIN, na dose de hoje

Leia como português: "das vendas, JUNTE produtos ONDE o id do produto bate com o produto_id da venda". O banco segue o post-it de ficha em ficha e devolve tudo numa linha só. É a única dose de JOIN do curso — e é a que resolve 80% dos casos. (JOINs de 3, 4 tabelas? Território do curso Fullstack. 😉)

➕
E o SUM? Primeira função de AGREGAÇÃO que você vê: em vez de devolver linhas, o banco calcula sobre elas — soma, na veia, direto no SQL. Existem primas (COUNT, AVG, MAX…) — fica o aperitivo.

BugZilla do dia: os perigos do id
Operações cirúrgicas pedem cirurgião atento
🐛
Bug 1 — o estoque negativo
Vendeu 50 fones tendo 12… e o banco aceitou

Sem a validação, o UPDATE faz 12 - 50 alegremente e seu estoque vira -38. Nenhum erro, nenhum aviso — só um sistema mentindo pro dono. O banco obedece; quem protege a regra do negócio é o SEU if.

💊 Remédio: validar ANTES de escrever (if qtd > produto[3]) — e o teste de aceitação é tentar quebrar: venda 500 de propósito no seu sistema. Barrou? Passou.

🐛
Bug 2 — a cirurgia na ficha errada
Editou o Mouse… e mudou o Teclado

Sintoma: salvou a edição e OUTRO produto mudou. Causa quase sempre: o action do form apontando pra URL fixa (/produtos/1/editar chumbado em vez de /produtos/{{ p[0] }}/editar) — todo salvar cai na ficha 1.

💊 Remédio: na tela de edição, olhe a URL: o número lá em cima é a ficha que será alterada. E confira se o action usa {{ p[0] }}, nunca número fixo.

🐛
Bug 3 — o formulário amnésico
Abriu a edição, tava tudo vazio… salvou assim mesmo

Esqueceu o value="{{ p[1] }}" nos inputs → o form de edição abre EM BRANCO. Quem não percebe e salva, substitui os dados reais por vazio — perda de dados por distração.

💊 Remédio: form de edição SEMPRE nasce preenchido (value= em cada input). Abriu vazio? Pare, não salve, conserte o template.

COUNT entra em campo
★★ médio COUNT

Missão final — Faturamento por produto
JOIN + SUM + uma pitada de GROUP BY
★★★ desafio JOIN SUM GROUP BY

Tabela "quanto cada produto rendeu": junte as duas queries que você já sabe e adicione GROUP BY produtos.nome no final — SELECT produtos.nome, SUM(vendas.total) FROM vendas JOIN produtos ON produtos.id = vendas.produto_id GROUP BY produtos.nome. O GROUP BY é o "some SEPARADO por cada nome" — aperitivo do que os relatórios de verdade fazem.
