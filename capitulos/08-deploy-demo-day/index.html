Preparando o app: 2 ajustes
Uma linha nova no fim do app.py — e uma conferência
🤖 O modo do curso continua valendo na nuvem

Você não altera o arquivo por impulso na última hora. Primeiro pede uma auditoria de deploy, limita o escopo, revisa o diff e testa a Loja localmente antes de compactar.

prompt de preparação para o deploy prompt 
Leia o arquivo de instruções do projeto e audite app.py para o deploy no PythonAnywhere.
Garanta que app.run(debug=True) só execute dentro de if __name__ == "__main__" e confirme
que existe secret_key para flash e login. Altere somente app.py e apenas se necessário.
Depois explique o diff e me passe testes locais. Não instale nada e não mude regras da Loja.

Ajuste 1: na nuvem, quem LIGA o seu app é a plataforma — o app.run() é só pra sua máquina. O jeito profissional de dizer isso em Python:

app.py — mapa para revisar o diff Python 
if __name__ == "__main__":
    app.run(debug=True)
💡 O if do "quem me chamou?"

__name__ vale "__main__" quando VOCÊ roda o arquivo (▶ no PyCharm) — aí o app.run liga o servidor local, como sempre. Quando o PythonAnywhere importa seu app, o if é falso e o app.run nem roda — a plataforma liga do jeito dela. Um if, dois mundos. (Você já viu esse padrão em código por aí — agora sabe o que ele faz.)

Ajuste 2 — conferência: seu secret_key está definido? (Sem ele, flash e login quebram na nuvem igual quebrariam local.) E o debug=True pode ficar — dentro do if, ele nunca roda no servidor público. ✅

PythonAnywhere, passo a passo

Do zip ao link público em 7 passos

🗺️
Os 7 passos (com o professor junto no telão)
Siga na ordem — cada passo tem seu checkpoint
1Conta gratuita — e o nome IMPORTA
Em pythonanywhere.com → Create a Beginner account (grátis). Atenção máxima ao username: ele vira sua URL pública pra sempre — SEUNOME.pythonanywhere.com. Escolha algo apresentável (o RH vai ver 👀). Confirme o e-mail.
2Compacte o projeto (SEM o venv!)
No seu computador, selecione só o conteúdo do projeto: app.py, banco.py, criar_banco.py e a pasta templates → botão direito → Comprimir → projeto.zip.
⚠️ NÃO inclua a pasta venv (são milhares de arquivos do SEU computador — a nuvem tem o Python dela) nem o loja.db (banco novo nasce lá, limpinho).
3Upload + unzip no console
Aba Files → botão Upload a file → mande o projeto.zip. Depois, aba Consoles → Bash (é um terminal — na nuvem!):
unzip projeto.zip -d loja cd loja python3 criar_banco.py
Checkpoint: o console imprime "Banco criado! 🗄️" — o loja.db nasceu NA NUVEM, na pasta certa.
4Criar o web app (Manual configuration)
Aba Web → Add a new web app → Next → escolha Manual configuration (NÃO o atalho "Flask"!) → Python 3.10 (ou o mais novo) → Next.
DashboardConsolesFilesWebDatabases
+ Add a new web app  →  Manual configuration → Python 3.10
Por que manual? Porque VOCÊ sabe configurar — o atalho esconde exatamente as partes que você entende.
5Apontar os caminhos (o passo que evita o BugZilla)
Ainda na aba Web, seção Code, preencha os DOIS campos com a pasta do projeto:
Web
Source code: /home/SEUNOME/loja
Working directory: /home/SEUNOME/loja
O working directory é ONDE o app "está parado" quando roda — é ele que faz o connect("loja.db") achar o arquivo certo. Lembra do no such table do Dia 3? É a mesma pegadinha, agora em produção. Este campo é o remédio.
6O arquivo WSGI — a ponte da plataforma
Na seção Code, clique no link do WSGI configuration file. Apague TUDO que está lá e deixe só isto (trocando SEUNOME):
import sys path = "/home/SEUNOME/loja" if path not in sys.path: sys.path.append(path) from app import app as application
Traduzindo: "Python, olhe na minha pasta… e o app do meu app.py é o aplicativo que você vai servir". É por ISSO que o if __name__ importa: aqui o seu arquivo é importado, não executado. Salve (o disquete verde).
7Reload — e o link existe 🎉
De volta à aba Web: o botão verde Reload SEUNOME.pythonanywhere.com. Clique. Espere os segundinhos. E abra:
🌍 seunome.pythonanywhere.com
🛍️ Minha Loja — no ar. Com login. Pro mundo.
Checkpoint final: logue, cadastre um produto, faça uma venda — NA URL PÚBLICA. Funciona? Respira. Você tem um sistema em produção.
🐛
BugZilla do deploy — os 3 de sempre
Todo deploy do mundo passa por isso. Sério.

① "Something went wrong :-(" → aba Web → Error log (o último erro fica no FINAL do arquivo). É um traceback Python — você lê traceback desde o Dia 1. 💊 90% das vezes: nome errado no WSGI (SEUNOME!) ou esqueceu o Reload.

② no such table: produtos → o velho conhecido: working directory não configurado (passo 5) ou esqueceu o criar_banco.py no console (passo 3). 💊 Conferir os dois → Reload.

③ ModuleNotFoundError: flask → raro no PythonAnywhere (o Flask já vem), mas se pintar: console Bash → pip3 install --user flask → Reload.

🔁
Atualizou o código depois? O ciclo é: upload do arquivo novo (ou edite direto na aba Files — tem editor!) → Reload. Sem reload, a nuvem continua servindo a versão antiga.
🛤️
Alternativa que você verá por aí: o Render (render.com) faz deploy direto do GitHub — mais "de mercado", porém pede Git, que não aprofundamos. Fica o nome anotado pra sua segunda subida. O conceito é idêntico.

A evolução: o que vem depois do monólito
Três perguntas que o seu sistema (ainda) não responde

Seu sistema é o que o mercado chama de monólito server-rendered: um Flask que faz tudo — telas E dados. Pra um negócio pequeno, é PERFEITO (e há empresas grandes rodando assim!). Mas três perguntas quebram ele:

📱 "E o app do celular?" app não renderiza template Jinja — ele precisa dos DADOS crus
👥 "E se o front for de outro time?" designer e dev de tela não querem mexer no seu Python
📈 "E com 10 devs e 1 milhão de usuários?" todo mundo no mesmo app.py? escala de gente e de máquina pedem separação

A resposta do mercado é separar — aperte o botão e veja:
