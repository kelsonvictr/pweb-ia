💡 Mesmo bolso, permanência diferente

O flash() guardava um bilhete de uma vez só: entregue na próxima página, e some. O login guarda um crachá que fica — request após request, até o /logout tirar do bolso. Mesma session, mesmo secret_key assinando pra ninguém falsificar. Você instalou a fechadura no Dia 5 sem saber que era fechadura.

🧠
Por que "assinado" importa aqui: um bilhete de sucesso falsificado é chato. Um crachá falsificado é invasão. É o secret_key que impede alguém de escrever usuario="admin" no próprio bolso e entrar. Aquela linha que você achou detalhe no Dia 5 virou a peça mais séria do sistema.

Nos Dias 4–5, cada prompt cobria uma operação: poucos arquivos, critério observável, teste em dois minutos. O login não cabe nesse recorte — ele atravessa banco, rotas, templates, sessão e segurança de uma vez. A solução não é aumentar o prompt: é quebrar a feature em três entregas que continuam cabendo na sua revisão. Cada aceite é uma catraca; o próximo prompt só passa depois do teste anterior.

A restrição que você repetiu três vezes 📌

Repare nos seus prompts do Dia 5: "SQL apenas no banco.py", "sem JavaScript", "sem biblioteca nova" — em todos eles. Restrição que se repete não é instrução de prompt: é regra do projeto. E regra do projeto mora no arquivo de instruções, que o agente lê sozinho antes de qualquer tarefa. Escreveu lá uma vez, vale pra sempre — inclusive pros prompts de hoje.

## Regras da Loja (CLAUDE.md ou AGENTS.md, na raiz do projeto) - Stack fixa: Flask + Jinja + sqlite3. Sem ORM, sem framework de CSS, sem JavaScript. - Todo SQL fica em banco.py, sempre com placeholder ? (nunca texto colado na query). - Uma operacao por vez: nao refatore nem "melhore" arquivos fora da tarefa pedida. - Nao execute scripts que alterem o loja.db. Os testes no navegador sao meus. - Ao terminar, explique o diff e pare. Nao siga para a proxima tarefa sozinho.

Entendendo o que o agente escreveu
Você não precisa saber ESCREVER isto hoje — precisa saber LER

O coração do login gerado é algo assim — acompanhe o destaque:

loja/app.py (gerado pelo agente — trecho) Python 
from werkzeug.security import check_password_hashfrom flask import session if check_password_hash(usuario[2], senha):    session["usuario"] = usuario[1]    return redirect("/produtos") @app.route("/produtos")@login_required
def produtos(): ...
🔒check_password_hash — compara a senha digitada com o hash guardado, do jeito seguro. Vem do werkzeug, que o Flask já traz.
🎫A session — o MESMO bolso assinado do flash() do Dia 5. Você já conhecia a peça-chave do login.
🧐A comparação certa: nunca senha == hash — o hash não "desfaz". A função confere sem nunca revelar a senha.
👤Logou? O nome vai pro bolso: session["usuario"]. Em qualquer request futuro, o servidor sabe quem é — até o /logout esvaziar o bolso.
🏷️@app.route fica acima de @login_required: assim o Flask registra a função já protegida. O crachá é conferido antes de a rota executar; sem crachá, redirect pro /login.
💡 Hash, em 20 segundos

Hash é um triturador de mão única: "trocar123" vira uma sopa de letras — e NÃO existe caminho de volta. No login, o sistema tritura o que você digitou e compara sopa com sopa. Nem o dono do site consegue ler sua senha — e é assim que TODO site sério funciona. (Site que te manda a senha por e-mail? Fuja. 🏃)

Prompt 5 — acabamento visual prompt
[CONTEXTO] Minha Loja tem static/style.css desde o Dia 3, mas as telas que nasceram depois (editar, excluir, vender, vendas e login) não têm regra nenhuma lá dentro e aparecem cruas. [TAREFA] Atualize SOMENTE o static/style.css para cobrir o que apareceu depois: o <select> e o campo de quantidade da tela de vender; os botões da página de confirmação de exclusão; o formulário de login; a tabela do histórico de vendas; o bloco de faturamento. [ACEITE] Todas as telas ficam visualmente coerentes entre si e NENHUM comportamento muda: cadastrar, editar, excluir, vender e logar continuam funcionando exatamente como antes. 🎯
Leia de novo a última linha do aceite: "nenhum arquivo .py e nenhum .html foi tocado". Esse é um critério que você confere só olhando a lista de arquivos do diff, em dois segundos, sem entender uma linha de CSS. Aceite bom é assim: verificável por quem não é especialista no assunto.
💡 Por que isso não foi um "capricho do professor"

Em todo projeto real acontece igual: a entrega urgente passa na frente, o acabamento fica pra depois, e o "depois" vira nunca. A diferença entre um time maduro e um time bagunçado não é ter dívida — é fechar a dívida a cada entrega, com escopo declarado. Você acabou de fazer isso com um prompt de cinco linhas.

🐛
Cuidado clássico deste prompt: o agente vai querer "aproveitar" e mexer nos templates pra facilitar a vida dele ("só adicionei uma classe aqui…"). Se o diff tocar em .html, rejeite: o aceite foi explícito. Fazer o CSS caber no HTML existente é justamente a parte difícil que você contratou.

Bug 1 — aceitar sem ler
"Tava tudo verde, aprovei" — famosas últimas palavras

O diff parecia bom, você apertou "sim" em tudo… e três dias depois descobre que o login não deixa ninguém entrar (o bug da caça, lembra?). Código gerado SEM revisão é bug agendado: vai estourar, só não se sabe quando.

Bug 2 — a espec vaga
"faz um sistema completo" = retrabalho completo

Pedidos gigantes e vagos produzem montanhas de código que NÃO é o que você queria — e aí você gasta mais tempo desfazendo do que gastaria fazendo. O agente não lê mente; lê espec.

💊 Remédio: uma feature por vez, com itens numerados e limites explícitos ("não mexer no que funciona", "não instalar bibliotecas"). A espec do login é seu modelo pra sempre.

Bug 3 — o que o agente RODA não aparece no diff
História real desta turma, no Dia 5 🫣

No meio da aula, o estoque começou a mudar sozinho: recarregava a página e apareciam produtos que ninguém tinha cadastrado; outros sumiam. A primeira suspeita caiu no navegador — "será que o F5 está cadastrando?". Não era.

O agente, para conferir se o que tinha acabado de implementar funcionava, escrevia e executava scripts de teste que apagavam a tabela produtos e inseriam produtos de exemplo — no mesmo loja.db que a turma estava usando ao vivo. Nada disso aparecia no diff, porque diff mostra o que ele ESCREVE nos seus arquivos, não o que ele EXECUTA.

💊 Remédio, em duas camadas: (1) leia também os comandos que o agente pede pra rodar, não só o diff — é onde mora esse tipo de estrago; (2) essa restrição não se repete a cada prompt: ela virou linha permanente no arquivo de instruções — "Não execute scripts que alterem o loja.db. Os testes no navegador são meus."
