Jinja: o template ganha lacunas
{{ assim }} — e o Python preenche na hora de servir
O diploma em branco 📜

Uma faculdade não desenha um diploma novo pra cada aluno. Ela tem UM modelo com lacunas — "certificamos que ______ concluiu o curso de ______" — e preenche na hora. O Jinja faz isso com HTML: o template é o modelo, as lacunas são {{ assim }}, e quem preenche é o seu Python, a cada request.

Funciona em dupla. No Python, você entrega os dados pro template como argumentos do render_template:

loja/app.py Python 
@app.route("/")
def home():
    return render_template("index.html",
                           nome_loja="Minha Loja",
                           destaque="Fone Bluetooth")

E no template, você usa as lacunas com o MESMO nome:

loja/templates/index.html Jinja 
<h1>🛍️ {{ nome_loja }}</h1>
<p>Destaque de hoje: {{ destaque }}</p>
💡 A regra do casamento de nomes

nome_loja= no Python ↔ {{ nome_loja }} no template. Mesmo nome dos dois lados, senão a lacuna fica vazia. As chaves duplas {{ }} são o Jinja dizendo "aqui entra dado do Python".

🕵️
Detalhe importante: o visitante NUNCA vê {{ nome_loja }}. O Jinja preenche as lacunas no servidor, antes da response sair. O navegador recebe HTML já pronto, sem sinal de Jinja. (Aperte F12 → "ver código-fonte" na sua página e confira!)

{% for %}: a linha de produção de HTML
Uma lista de produtos no Python → uma tabela inteira na tela

E quando o dado não é UM valor, mas uma lista? Seus produtos, por exemplo — uma lista de dicionários, igualzinho ao bootcamp:

loja/app.py Python 
produtos = [
    {"nome": "Fone Bluetooth",   "preco": 149.90},
    {"nome": "Teclado Mecânico",  "preco": 299.00},
    {"nome": "Mouse Gamer",       "preco": 89.90},
]

@app.route("/")
def home():
    return render_template("index.html", produtos=produtos)

No template, o Jinja tem um {% for %} — primo do for do Python que você já domina. Tudo que estiver entre o {% for %} e o {% endfor %} é carimbado uma vez por item:

loja/templates/index.html Jinja 
<table>
  <tr><th>Produto</th><th>Preço</th></tr>
  {% for p in produtos %}
    <tr>
      <td>{{ p["nome"] }}</td>
      <td>R$ {{ p["preco"] }}</td>
    </tr>
  {% endfor %}
</table>
🆕
Tags novas na área: <table> é a tabela, <tr> é uma linha (table row), <th> é célula de cabeçalho e <td> é célula de dado. Aninhamento em ação: td dentro de tr, tr dentro de table.

Veja a linha de produção rodando devagar:

🧩 o carimbo (dentro do for)
esperando ▶ …
{% for p in produtos %} <tr> <td>{{ p["nome"] }}</td> <td>R$ {{ p["preco"] }}</td> </tr>{% endfor %}

ProdutoPreço

Uma linha de template gera 3, 30 ou 3.000 linhas de tabela — depende só da lista. Produto novo no Python? A tela atualiza sozinha no F5. Adeus, cartaz.

{% if %}: o plano B na tela
E se a lista estiver vazia? O aluno de vendas nunca esquece o caso triste.

Imagina a loja recém-aberta, sem produtos: produtos = []. O {% for %} roda zero vezes e a pessoa vê… uma tabela vazia, sem explicação. Feio. O Jinja também tem {% if %}:

loja/templates/index.html Jinja 
{% if produtos %}
  <table> … a tabela com o for aqui … </table>
{% else %}
  <p>😢 Estoque vazio! Cadastre o primeiro produto.</p>
{% endif %}
💡 Lista vazia é "falsa" — igual no Python

{% if produtos %} segue a regra que você aprendeu no bootcamp: lista com itens = verdadeiro, lista vazia [] = falso. O mesmo raciocínio, agora decidindo o que aparece na tela.

✍️
Pegadinha de digitação: as tags de comando usam {% %} (com porcento) e as de valor usam {{ }} (chaves duplas). Misturar as duas é o erro de digitação nº 1 do Jinja — e TODO for/if precisa do seu {% endfor %}/{% endif %}.

Anatomia do <form>
O balcão de atendimento da sua página

Todo cadastro, login e busca da internet começa igual: um formulário. Ele é HTML puro — três tags novas e nenhum mistério:

o formulário de cadastro HTML
1
2
3
4
5
<form action="/" method="POST">
  <input name="nome" placeholder="Nome do produto">
  <input name="preco" placeholder="Preço">
  <button>Cadastrar</button>
</form>
📮 action PRA ONDE o request vai quando apertar o botão (qual URL/rota)
🚚 method COMO o request viaja: GET ou POST (já já isso vira importante)
🏷️ name a ETIQUETA de cada dado — é por ela que o Python vai pescar o valor
🔘 <button> dentro de um form, o botão SUBMETE: empacota os dados e envia
🏷️
O name é a estrela. Input sem name viaja SEM ETIQUETA — o dado chega no servidor e ninguém sabe o que é (na prática: não chega). Grava: todo input tem name.
👁️
placeholder é só a dica cinza dentro do campo — não viaja com o form. Quem viaja é o par name="nome" + o que a pessoa digitou.
⭐
GET vs POST: cartão-postal ou envelope lacrado
Clique nas abas e repare na barra de endereço
De volta ao restaurante 🍝

GET é pedir o cardápio: "me MOSTRA algo" — pedido simples, aberto, pode repetir à vontade. POST é entregar o pedido preenchido: "toma, PROCESSA estes dados" — carrega conteúdo, muda as coisas na cozinha.

A mesma submissão do form, nos dois métodos — repara na URL e no envelope:

📄
📄 GET dados na URL, visíveis; pra BUSCAR/mostrar; F5 repete sem perigo
✉️ POST dados no corpo do request; pra CRIAR/mudar algo; URL fica limpa
💡 A regra prática

Vai só ler/mostrar? GET. Vai cadastrar, alterar, enviar senha? POST. Formulário de cadastro, portanto: method="POST" — sempre.

🙈
Nunca senha em GET! Dados de GET ficam na URL — que aparece na tela, no histórico e nos registros do servidor. Imagina /login?senha=123456 no histórico do navegador da lan house. 💀

request.form: o Python abre o envelope
Os dados chegaram — como pegar cada um?

Duas novidades no app.py. Primeira: a rota precisa aceitar POST (por padrão, rota Flask só aceita GET — segurança). Segunda: o Flask entrega os dados do form num objeto chamado request.form, que funciona como um dicionário:

loja/app.py Python

from flask import Flask, render_template, request, redirect

@app.route("/", methods=["GET", "POST"])
def home():
    if request.method == "POST":
        nome  = request.form["nome"]
        preco = float(request.form["preco"])
        produtos.append({"nome": nome, "preco": preco})
        return redirect("/")

    return render_template("index.html", produtos=produtos)
💡 O casamento de nomes, parte 2

name="nome" no HTML ↔ request.form["nome"] no Python. A etiqueta do input vira a chave do dicionário. Mesmo nome dos dois lados — igualzinho à regra do Jinja.

🔢
Tudo chega como texto! Mesmo que a pessoa digite 149.90, o form entrega "149.90" (string). Por isso o float(...) — você já fazia igual com o input() no bootcamp. Nada mudou. 😉
↩️
E o redirect("/")? Depois de cadastrar, mandamos o navegador "vai pra home de novo" — que recarrega a tabela já com o produto novo. O PORQUÊ profundo desse redirect (e o bug que ele evita) é assunto nobre do Dia 4. Por ora: cadastrou → redirect.

BugZilla do dia: a dupla do formulário
Os dois erros que TODA turma encontra no dia de forms
🐛
Bug 1 — Method Not Allowed (405)
Você apertou Cadastrar e o Flask bateu a porta
navegador erro 
Method Not Allowed
The method is not allowed for the requested URL.

Tradução: o form mandou um POST, mas a rota só aceita GET — porque faltou o methods=["GET", "POST"] no @app.route. O Flask nem deixou o request entrar.

💊 Remédio: @app.route("/", methods=["GET", "POST"]) — e confere se o action do form aponta pra essa rota mesmo.

🐛
Bug 2 — KeyError: 'nome'
O Python procurou a etiqueta e ela não existia
navegador — tela de erro do Flask erro 
File "app.py", line 12, in home
    nome = request.form["nome"]
KeyError: 'nome'

O request.form é um dict — e KeyError em dict você já conhece do bootcamp: a chave não existe. Aqui significa: nenhum input do form tem name="nome". Ou o name está escrito diferente (name="Nome"? maiúscula conta!), ou… você esqueceu o name de vez.

💊 Remédio: compare LETRA POR LETRA o name="..." do input com o request.form["..."] do Python.

🎁
Bônus sorrateiro — o form "mudo": tudo funciona, nada dá erro… mas o produto chega vazio. Causa clássica: input sem name (o dado nem viaja). Erro silencioso é o pior tipo — confere os names primeiro.

Missão final — A busca da loja
Um form GET fazendo sentido
★★★ desafio GET request.args if

Crie uma página /buscar com um form method="GET" e um input name="q". No Python, pegue o termo com request.args.get("q", "") (o primo do request.form pra dados de GET) e mostre só os produtos cujo nome contém o termo. Repare na URL depois de buscar: /buscar?q=fone — o GET na prática, e dá até pra mandar o link da busca pra alguém!

💡 Dica do filtro

No Python do bootcamp: encontrados = [p for p in produtos if q.lower() in p["nome"].lower()] — ou um for com if, do jeito clássico. Os dois valem.
