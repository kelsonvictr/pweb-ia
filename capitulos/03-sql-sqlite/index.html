O caderninho vs. o fichário de aço
Com todo respeito ao TinyDB — ele te trouxe até aqui
A mercearia e o mercado 🏪

Uma mercearia pequena anota vendas num caderninho: funciona! Mas o mercado grande tem um fichário de aço indexado: acha qualquer ficha em segundos, várias pessoas consultam ao mesmo tempo, e nada se perde nem rasga. Seu sistema está crescendo — chegou a hora do fichário.

📓 TinyDB (o caderninho)
🐌Volume: relê e regrava o JSON INTEIRO a cada operação — 10 mil produtos = sofrimento
🔦Busca: percorre tudo na unha pra achar um registro
💥Concorrência: dois acessos gravando juntos = risco de arquivo corrompido
🤷Mercado: nenhuma vaga pede TinyDB
🗄️ SQLite (o fichário de aço)
🚀Volume: mexe só no pedacinho certo do arquivo — milhões de linhas, numa boa
🎯Busca: índices — acha 1 registro entre milhões sem varrer tudo
🔒Concorrência: controla os acessos pra ninguém corromper nada
💼Mercado: SQL é exigência em praticamente TODA vaga de backend e dados
💡 O superpoder de hoje não é o SQLite. É o SQL.

SQL é a língua universal dos bancos relacionais — a MESMA que você usaria com PostgreSQL, MySQL, Oracle… Aprendeu uma vez, usa em qualquer emprego. O SQLite é só o nosso primeiro carro pra treinar a direção.

📋
Tabelas, colunas, linhas
Uma planilha turbinada — com regras rígidas de propósito

Um banco relacional organiza tudo em tabelas — como uma planilha: cada coluna é um campo com nome e tipo, cada linha é um registro. A tabela da Loja vai ser assim:

idnomeprecoquantidade
1Fone Bluetooth149.912
2Teclado Mecânico299.05
3Mouse Gamer89.923
🗂️ Tabela um "assunto": produtos, clientes, vendas — cada um na sua
📐 Coluna um campo com nome E tipo fixo (nome é texto, preco é número)
📄 Linha um registro completo — o dict do bootcamp, domado
🔑 id o número único de cada linha — o "número da ficha"
🆚
Diferença pro TinyDB: lá, cada dict podia ter as chaves que quisesse (um produto com preço, outro sem…). No relacional, a tabela define as colunas UMA vez e toda linha obedece. Essa rigidez parece chata — é ela que deixa o banco rápido e confiável.
📱
SQLite: o banco que está no seu bolso agora
Sério. Pega o celular. Ele está cheio de SQLite.

O SQLite é um banco relacional completo que vive num único arquivo (o nosso vai chamar loja.db) e já vem com o Python — zero instalação. E não é banco "de brinquedo":

💬 WhatsApp (suas conversas) 📸 galeria de fotos 🎵 apps de música 🌐 histórico do navegador 🎮 saves de jogos ✈️ sistemas de avião

É provavelmente o software mais implantado do mundo — bilhões de cópias rodando agora. E hoje ele trabalha pra você. 😎

💡 Um arquivo = o banco inteiro

Tabelas, dados, índices… tudo dentro do loja.db. Quer backup? Copia o arquivo. Quer levar pro deploy? Vai junto. Essa simplicidade é o motivo de ele ser perfeito pra aprender — e pra MUITO sistema em produção.

Parte 2

Criando a tabela

A primeira frase de SQL da sua vida

🏗️
CREATE TABLE: desenhando o fichário
Clique em cada pedaço do comando — igual fizemos com a URL

Antes de guardar qualquer coisa, você declara o formato das fichas: quais colunas, de que tipo. Esse é o primeiro comando SQL da sua vida — e cada pedaço dele tem um porquê:

CREATE TABLE produtos ( id INTEGER PRIMARY KEY AUTOINCREMENT, nome TEXT, preco REAL, quantidade INTEGER )
👆 Clique em cada pedaço do comando (ou espere o passeio automático).
💡 Todo dado tem tipo — e o banco COBRA

TEXT = texto (a string do Python) · INTEGER = número inteiro · REAL = número com vírgula (o float). No Python o tipo é implícito; no banco você declara na criação da tabela — e é essa disciplina que permite busca rápida e dados confiáveis.

🪄
AUTOINCREMENT é mordomia: você nunca vai inventar id. Insere a primeira linha → o banco carimba 1. A próxima → 2. Pra sempre único, sem você pensar nisso. (Guarde esse id: ele brilha MUITO no Dia 5.)
🔍
O espião: DB Browser for SQLite
Uma ferramenta opcional pra VER o arquivo por dentro

O loja.db é um arquivo binário — abrir no PyCharm mostra só um monte de caractere estranho. O DB Browser for SQLite (sqlitebrowser.org, grátis) abre o arquivo e mostra as tabelas como planilha, com uma aba pra executar SQL. Ótimo pra conferir com os olhos o que seus scripts fizeram.

🧭
Mas o caminho principal é o Python. O DB Browser é o espião, não o motorista: usaremos ele só pra espiar. Quem cria, insere e consulta — em aula e no seu sistema — é o seu código. (E atenção: deixar o DB Browser aberto segurando o arquivo pode travar seu script… guarda essa, o BugZilla volta nisso.)

Os 4 verbos do SQL

Criar, ler, mudar, apagar — o vocabulário completo do fichário

⭐
Simulador SQL: execute e veja a tabela reagir
Cada aba é um verbo. Rode todos — inclusive fora de ordem.

Esta é a tabela produtos viva. Escolha um comando nas abas, aperte ▶ Executar e observe o efeito. Errou a ordem? Usa o 🔄 e recomeça.

idnomeprecoquantidade
começa pelo INSERT — cadastre a caixa de som
➕ INSERT nova ficha no fichário (o .append de gente grande)
👀 SELECT ler fichas — todas, ou filtradas com WHERE
✏️ UPDATE corrigir uma ficha que já existe (SEMPRE com WHERE!)
🗑️ DELETE rasgar uma ficha (SEMPRE com WHERE — ou adeus, tabela)
☠️
A lenda do UPDATE sem WHERE: UPDATE produtos SET preco = 1 (sem WHERE) muda o preço de TODOS os produtos. DELETE FROM produtos (sem WHERE) apaga TUDO. Todo dev sênior tem uma história de terror dessas. Regra de sobrevivência: UPDATE e DELETE andam SEMPRE com WHERE.
📖
SQL se lê como inglês: "SELECT nome FROM produtos WHERE preco < 100" = "selecione o nome, dos produtos, onde o preço é menor que 100". Maiúsculas nos comandos são convenção (funciona minúsculo, mas todo mundo escreve assim).

SQL dentro do Python

O módulo sqlite3 — já instalado, esperando você

🐍
O ritual do sqlite3
Conectar → cursor → executar → salvar → fechar. Sempre essa dança.

Hoje o projeto é outro: File → New Project… com o nome treino-sql (sem Flask, sem templates — só Python e SQL). Dentro dele, New → Python File chamado criar_banco.py. Acompanhe o destaque — o ritual tem 5 passos e vai se repetir a vida inteira:

treino-sql/criar_banco.py Python 
import sqlite3 conexao = sqlite3.connect("loja.db")cursor = conexao.cursor() cursor.execute("""
    CREATE TABLE IF NOT EXISTS produtos (
        id INTEGER PRIMARY KEY AUTOINCREMENT,
        nome TEXT,
        preco REAL,
        quantidade INTEGER
    )
""") conexao.commit()conexao.close() print("Banco criado! 🗄️")
📦import sqlite3 — já vem com o Python. Nada de pip install hoje!
🔌connect abre (ou CRIA, se não existir) o arquivo loja.db. A conexão é o cabo ligando seu script ao cofre.
🖱️O cursor é a "mão" que mexe no banco — é ele que executa comandos e pega resultados.
⚡execute roda o SQL — o MESMO CREATE TABLE do simulador, numa string de três aspas. O IF NOT EXISTS deixa rodar o script de novo sem erro.
📌commit = CARIMBAR no arquivo. Sem ele, mudanças ficam só no rascunho… (a próxima máquina mostra o desastre)
🚪close desliga o cabo, liberando o arquivo. Abriu, usou, fechou — educação de dev.
🎉Rode com botão direito → Run 'criar_banco' — e repare: nasceu um arquivo loja.db na árvore de arquivos!

Cada linha vem como (1, 'Fone Bluetooth', 149.9, 12) — uma tupla na ordem das colunas: id, nome, preco, quantidade. Então p[1] é o nome, p[2] o preço. Guarde isso: o Dia 4 usa direto no template.

🕵️
Leitura não precisa de commit — carimbo é só pra ESCRITA (INSERT/UPDATE/DELETE e CREATE). O SELECT só olha as fichas; não mudou nada, nada a salvar.
⭐
Rascunho e Carimbo: o segredo do commit
Execute escreve a lápis. Commit passa a caneta. Teste os dois destinos.

Quando você dá execute num INSERT, o SQLite anota num rascunho (a "transação"). Só o commit() carimba de verdade no arquivo. Rode o INSERT e escolha o final da história:

📝 o rascunho (na memória)
rascunho da transação(vazio — rode um INSERT)
🗄️ loja.db (o arquivo de aço)
🔒 produtos
(1, 'Fone Bluetooth', 149.9, 12)
primeiro o execute — escreve no rascunho
💡 Por que existe o rascunho?

Imagine transferência bancária: tirar R$ 100 de uma conta E pôr na outra. Se o sistema cair NO MEIO, não pode ficar pela metade! O rascunho permite fazer as duas coisas e carimbar tudo junto, ou nada. Chama-se transação — hoje basta saber: escreveu? commita.

🛡️
O ? que salva seu banco
Por que NUNCA colar texto do usuário dentro do SQL

No Dia 4, quem digita o nome do produto é o visitante. E se um visitante mal-intencionado digitar… um pedaço de SQL? Veja os dois destinos do mesmo input maligno:

👤 o "cliente" digitou no formulário: Fone'); DELETE FROM produtos; --
❌ colando na string (f-string)
f"INSERT INTO produtos (nome) VALUES ('{nome}')"
aperte ▶ pra ver o estrago…
✅ com placeholder ?
execute("INSERT INTO produtos (nome) VALUES (?)", (nome,))
o mesmo input, dois códigos diferentes
💡 SQL injection — agora você conhece o golpe

Colar input na string deixa o usuário escrever SQL no seu banco — esse golpe (SQL injection) já vazou dados de empresas gigantes. Com ?, o SQLite trata o input como DADO, nunca como comando: o texto maligno vira só um nome de produto esquisito na tabela. Regra inegociável do curso: valor de fora → placeholder ?, sempre.

BugZilla do dia: os fantasmas do banco
Incluindo o pior tipo de bug: o que NÃO dá erro
🐛
Bug 1 — o commit esquecido (SILENCIOSO ☠️)
Rodou, não deu erro… e não salvou nada

Você roda o inserir.py sem o commit(): nenhuma mensagem de erro. Tudo parece bem. Aí roda o consultar.py e… a tabela está vazia. O INSERT ficou no rascunho e evaporou no close() (você VIU isso na máquina do Rascunho e Carimbo).

💊 Remédio: desconfie de "funcionou mas não salvou" → procure o commit(). Mantra do dia: escreveu no banco? Carimba.

🐛
Bug 2 — no such table: produtos
O banco certo… no lugar errado
terminal erro 
Traceback (most recent call last):
  File "consultar.py", line 6, in <module>
    cursor.execute("SELECT * FROM produtos")
sqlite3.OperationalError: no such table: produtos

Pegadinha cruel: connect("loja.db") procura o arquivo na pasta do script que está rodando — e se não achar, CRIA UM NOVO, vazio! Script numa subpasta diferente da do criar_banco.py? Nasceu um segundo loja.db zerado, sem a tabela.

💊 Remédio: olhe a árvore de arquivos do PyCharm — se tiver mais de um loja.db, é esse o problema. Mantenha todos os scripts do dia na mesma pasta, do lado do banco. (Se quiser conferir, o caminho completo aparece no topo da janela Run.)

🐛
Bug 3 — database is locked
Alguém está segurando o fichário

Seu script trava com sqlite3.OperationalError: database is locked. Causa clássica em aula: o DB Browser aberto com alterações não salvas, segurando o arquivo. O espião virou sequestrador.

💊 Remédio: no DB Browser, "Write Changes" (ou feche o programa) e rode de novo.
